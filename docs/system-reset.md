# Owner-only BillFlow reset

Settings now contains a ล้างข้อมูลระบบทั้งหมด card. The scope is all BillFlow ledger data and receipt files belonging to the currently signed-in shop owner. Other users' ledgers, Auth accounts, menu grants, LINE pairing credentials and OCR credentials remain. LINE delivery is temporarily switched off only inside the reset transaction while replacing the ledger, preventing deletion notifications; its current value is then restored before commit. The UI discloses the scope and permanent removal before the request begins.

1. `billflow_begin_reset` requires the workspace owner, a confirmed email, and an existing unexpired Auth session matching JWT session_id. It binds a one-time challenge to owner, session, email and current ledger revision. Requests are limited to one per minute and five per hour.
2. The client calls `supabase.auth.reauthenticate()` to send the existing Supabase SMTP reauthentication OTP to that account's email. No email address can be supplied or overridden by the reset form. Delivery errors stop progress.
3. The user enters the email OTP and the exact phrase `ล้างข้อมูลทั้งหมด`. Both are checked on the server. Challenge lifetime is ten minutes and wrong attempts persist, with a maximum of five. Verification checks a fresh Auth reauthentication nonce sent after this challenge to the same confirmed email, using SHA-224(email + nonce), matching Supabase Auth's implementation (`internal/api/reauthentication.go`, `internal/api/mail.go`, `internal/crypto/crypto.go`). An unsupported future token format fails closed. No Auth token is returned to the browser or changed by the reset.
4. Confirmation checks ownership/session again, locks the challenge and ledger, rejects revision changes, and waits for active OCR/LINE work to finish. In one transaction it snapshots existing own receipt paths into a private cleanup job, temporarily suppresses LINE delivery, removes this owner's inbox/outbox records, restores the default empty payload, increments the revision and consumes the challenge. It never resets the revision counter, preventing stale tabs from restoring old data.
5. Storage deletion uses the Storage API through the authenticated or worker-authenticated `billflow-reset-cleanup` Edge Function. It only removes paths previously snapshotted under the same owner's prefix in `billflow-receipts`; other buckets and newly uploaded paths are unaffected. Failed cleanup retains remaining paths and retries via a minute cron job, up to ten claims. The settings page displays remaining files and failures. No direct SQL deletes of storage.objects are performed.

Deployment: `supabase/system-reset.sql`, Edge Function `billflow-reset-cleanup` with self-verified user/worker authentication. Private challenge/job tables have no client grants. Public client wrappers delegate to owner-checking private functions. Path claim/finish functions are service-only.

Validation: 41 unit tests and the production build pass. `tests/system-reset.sql` creates synthetic users and sessions, temporarily uses an isolated fixture owner within a rolled-back transaction, and tests phrase mismatch, nonce mismatch/freshness, expiry, five durable failed attempts, cooldown, cross-session rejection, session expiry, revision conflict, valid reset, replay, owner-only access and service-only resumable cleanup. It verifies the real owner's payload/revision is unchanged, and rolls back every fixture. No real owner email challenge was requested and no real ledger reset was performed. The existing SMTP channel is used when the owner clicks the button. Browser preview infrastructure was unavailable, so visual browser QA was not performed.

## Preserve the latest setup and owner email

`supabase/reset-preserved-settings.sql` retains the exact latest LINE settings, including enabled, credentials, group, webhook and unexpired pairing challenge, and the latest encrypted Gemini key reference/model. The owner-only `billflow_preserved_setup` exposes status and email without returning secrets. The reset test now snapshots synthetic LINE/Gemini settings after changing them, resets the synthetic ledger, and verifies byte-for-byte equality of those configuration rows, no deletion notices, and the latest confirmed owner email after an email change.

The settings card offers changing the email of the existing owner account via Supabase Auth email confirmation, preserving its UID and all data/configuration. This changes that account’s login email and requires an unused email address; it does not transfer the shop to a different existing registered account. No live email change or verification message is sent while implementing this feature. Ownership remains assigned to the same account ID; the current confirmed Auth email is read afresh rather than restored from a hardcoded address.

An initial proposal to expose the owner contact email before login was rejected by automatic approval review. The shipped design restricts setup/email data to the authenticated owner and shows no owner email on the public login page.


## Reset every data menu to defaults (October 30, 2026)

Apply `supabase/reset-all-menus.sql` after the other BillFlow SQL files. It replaces the shop ledger atomically after the existing owner, confirmed-email, active-session, OTP, phrase and revision checks. The new row uses revision + 1 and a canonical empty payroll, numbering, recurring-expense and contact state. Normal UPDATE validation and immutable approved payroll/journal protections remain unchanged. Explicit reset no longer uses the legacy accounting block. Each repeat reset starts from the same canonical payload.

Shop business details, logos, signatures, QR images, employees, entries, debts, payroll, journals, chart customizations and attached receipt files are reset. Old payroll-share records and the owner's deleted custom-photo pointer are removed. Storage cleanup uses the original same-owner path snapshot and Storage API; it never deletes Storage metadata through SQL. CORS supports both official frontend origins. The UI reports pending file cleanup separately.

Login accounts, user permissions, LINE/OCR/SSO connections, central usage audit history and existing private archived backups remain. The ledger's legacy audit list is empty after reset; a new central reset event records the operation. Other users' records and other application buckets remain untouched.

Validation runs exclusively in isolated PGlite using read-only snapshots of deployed validators. It covers approved and paid payroll, posted journals, repeated reset, OTP/session/revision checks, atomic rollback on failed INSERT, same-owner file snapshots, preserved connections/history and unaffected outsider records. No real OTP or real reset is submitted during installation. Old pending reset dialogs are cancelled so the owner requests a fresh OTP after deployment.
