# Usage history

Settings replaces the old recent-history card with an owner-only audit table containing actor name/email snapshots, server time (displayed in Asia/Bangkok), action, record reference, authenticated-session IP, browser device reference, user agent and source. Filters include date range, name/email, IP, device, record ID and action. Results use keyset pagination (100 at a time), and loaded rows can be exported as formula-safe CSV. The older local audit array remains separately visible before the detailed recorder's start time; missing old identity/IP/device data is not invented.

Database events are appended by triggers for successful ledger changes, permissions, LINE settings, Gemini settings, LINE inbox workflow, final LINE delivery outcomes and completed resets. Ledger events identify changed collections/record IDs and field names; no financial field values, document contents, contact details, images, credentials, passwords or OTPs are copied. Bulk changes record at most 200 per-record metadata events plus a bulk/revision event. Bookkeeping changes have their own revision event.

Browser-reported events cover successful password login, logout requests, menu opening, exports/backups, attachment upload/open requests, LINE actions, reset-code requests and owner-email change requests. These are labelled separately from confirmed database mutations, limited to 120 per actor per minute, and may be absent if the browser closes or a request fails. Actors are always taken from the authenticated request. Context is enumerated or discarded rather than storing arbitrary input. API/credential bodies are never passed to the recorder.

IP is read from the matching `auth.sessions` row, not trusted from a caller-supplied forwarding header. It is the latest IP known to Auth for that session, not proof of a physical location or necessarily the IP of each individual request. Server/LINE events without an authenticated session show no user IP/device. The device reference is a random UUID stored in localStorage and carried in the already-supported `x-client-info` header; it is browser-managed and can be changed by clearing storage or spoofed by a client. It is not an IMEI, hardware serial or proof of a unique physical device.

Events are kept in `billflow_private.usage_events`, outside the ledger/reset payload. Client roles have no table insert/update/delete/select grants. Only the owner-checking history RPC can read them; append helpers are private, and browser events cannot supply an actor identity. Snapshot identity remains after account details change. Financial resets retain these security/reference events. There is no client deletion or editing UI/API. Database administrators still control the underlying database.

Migrations: `supabase/usage-history.sql`, `supabase/usage-history-coverage.sql`. Validation includes unit tests and the production build, rolled-back synthetic SQL checks for authoritative session IP, device metadata, actor name, mutation fields, arbitrary-context redaction, owner-only reading, rejection of client updates/deletes/direct actor-forging, event retention after clearing financial data, and regression checks for reset/recurrence workflows. No real user account or ledger was reset by testing. Browser visual QA was unavailable.

Brand subtitle also corrected to the exact requested `by PUROnGAIR`.

## Device type display

The history table now shows a separate device column: computer, mobile, tablet, automatic system, or unknown, plus an inferred operating system and browser. CSV exports include the same three fields while retaining the original user agent. These labels are derived from the already-stored user agent, so existing detailed records can display them without rewriting the audit log or collecting additional device data. Edge/Opera/Samsung/Firefox signatures are checked before overlapping Chrome/Safari signatures. Android without Mobile and explicit iPad/Tablet identifiers classify as tablets. Generic/empty clients remain unknown; server-origin events are automatic system events.

The UI explains this is an estimate based on browser-reported data and may be wrong in desktop mode or with spoofed user agents. It does not identify a physical laptop/desktop model or guarantee distinction between iPad desktop mode and a Mac. Representative regression cases cover Windows Chrome/Edge, iPhone Safari, iPad Safari, Android phone/tablet, Samsung Internet, macOS Firefox, empty/unknown user agents and system events. Production build and 62 tests pass.
